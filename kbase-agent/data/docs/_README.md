把你要喂给 Agent 的业务文档放进本目录，`app/retrieval/loader.py` 统一解析后**一起切分、一起进 chroma 索引**。支持 `.md` / `.txt`（UTF-8 直读）、`.docx`（段落+表格）、`.xlsx`（各工作表转文本行）、`.pdf`（文本层抽取；扫描件/图片 PDF 需 OCR，列为扩展）。文件名以 `_` 开头的文件会被 loader 忽略（如本文件），只用于写说明、不参与建索引。

## 语料构成

当前语料共 **39 篇**：原有 9 篇 + 为"让检索评测有区分度"而扩充的 30 篇。全部是**合成的企业制度/FAQ 示例**（文件名统一带 `_示例`），不是任何真实公司的文件。

| 类别 | 篇数 | 覆盖内容 |
|---|---|---|
| 员工与人事制度 | 14 | 员工手册、入职转正与离职、考勤与打卡、病假与医疗期、婚育假与育儿假、弹性工作与远程办公、值班与应急值班、员工福利与体检、薪酬结构与个税申报、绩效改进与申诉、晋升与内部转岗、实习生与劳务派遣、竞业限制与保密、员工投诉与举报 |
| 财务与行政 | 7 | 薪酬与绩效、差旅与出差、业务招待费与礼品、发票与税务合规、采购与供应商、合同评审与用印、培训与认证补贴 |
| 信息安全与IT | 4 | IT与账号管理、信息安全与数据分级、软件正版化与IT资产、账号权限与访问审批 |
| 产品与交付 FAQ | 8 | 产品FAQ、产品交付与售后、产品计费与订阅、产品性能与容量规划、产品升级与版本发布、产品审计与操作日志、产品数据导入导出、技术支持与工单流程 |
| 运维与合规 FAQ | 3 | 数据备份与灾备、等保与合规认证、客户成功与续约 |
| 其它格式样例 | 3 | `OA操作指引.docx`、`绩效系数对照表.xlsx`、`入职材料清单.pdf`（验证多格式解析链路） |

> **为什么文档数量比"知识量"更重要**：原始 9 篇只有 10 个分块，40 条金标的 `topk_hit_rate` 三条检索路**全是 1.0**——评测完全没有区分度，"用了混合检索"这句话没有任何数据支撑。扩到 39 篇 / 40 分块后，仅向量掉到 0.875、仅 BM25 掉到 0.964、RRF 仍是 0.982，**混合检索的收益第一次被自己的 harness 测出来**（详见 `kbase-agent/README.md` 的「检索路消融」）。
>
> 关键不是"加得多"，而是**加得难区分**：新增文档刻意与金标问题共享话题词（例如《差旅与出差管理办法》与《员工手册》都讲"出差住宿"，但前者只规定境外与用车），这样才能制造真实的词面竞争。若只是加入一批互不相干的文档，三条路依然都是 1.0。

## 使用注意

- **新增 / 替换 / 删除** 任意文档后，直接重跑 `python scripts/index_docs.py` 即可。
  它是**全量重建**（先清空 collection 再全量写入），不是增量入库——所以增删替换都走同一条命令，
  也不需要手工删 `data/chroma/`。语料只有几十个分块时，全量重建本来就是最省事也最不容易错的做法。
- 目录里**只索引顶层文件**，子目录不会被索引；文件名以 `_` 开头的不参与索引。
- 解析失败或没有任何文本层的文件会被跳过，**但每次跳过都会打一条 WARNING 日志**——
  建索引后看一眼日志，能立刻发现"某个文档其实没进去"。
- **改了语料必须同步检查金标**：`eval/questions.jsonl` 里 `expected_source` / `expected_sources`
  指向的文档若被改名或删除，评测会静默变成全 miss。金标里的事实必须仍然只出现在它声明的那份文档里，
  否则真值就不唯一了。
- 改了金标关键词或应拒答的"编造特征"只需 `python scripts/eval_e2e.py --reanalyze` 离线重算，不必重新调模型（零成本）。
